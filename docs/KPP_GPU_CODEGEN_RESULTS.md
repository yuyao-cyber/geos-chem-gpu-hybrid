# KPP GPU code-generation mode (`#ACCDIRECTIVES`)

**Goal.** Make the KPP code generator emit GPU-ready (OpenACC) solver code
natively, replacing the post-hoc `batch_src/patch_sources.py` pass that the
batched GPU solver pipeline previously required.

**Status: COMPLETE — generator work done; CPU gate passed; GPU run passed
(collected 2026-09-02 after the VPN outage).** All three
patch_sources.py transformations are emitted natively by KPP itself; no
post-processing pass is needed. Stock output (without the flag) is
byte-identical to the KPP 3.3.0 baseline.

## What upstream had

Nothing. Grepped KPP 3.3.0, 3.5.0 (latest tag), and `main` of
`KineticPreProcessor/KPP` for `openacc`, `acc routine`, `cuda`, `gpu` in
`src/` and `docs/`: zero hits. There is no OpenACC/GPU support of any kind
upstream, so this mode was built from scratch on top of the existing
autoreduce (`#AUTOREDUCE`) machinery. (`geoschem/KPP` on GitHub is a
frozen KPP-2.2.3 fork that redirects to `KineticPreProcessor/KPP`; the 3.3.0
tag lives in the latter, matching the `Generated by KPP-3.3.0` headers of the
GC 14.7.1-era standalone sources.)

## How to invoke

Add one line to the mechanism's `.kpp` file (same style as `#AUTOREDUCE`):

```
#ACCDIRECTIVES on
```

Default is `off`. With `off` (or the line absent) the generator output is
byte-identical to stock KPP 3.3.0 — verified, see below. A GEOS-Chem build
could enable it by sed-ing the line into `gckpp.kpp` or committing a GPU
variant of the file.

## What the mode emits (exactly the patch_sources.py surgeries)

With `#ACCDIRECTIVES on` (F90 target), three generated files change and no
others:

1. `gckpp_Function.F90`
   - `!$acc routine seq` after the SUBROUTINE line of `Fun`, `Fun_SPLIT`,
     `Fun_SPLITF`, `CalcStoichNum` (all subroutines in the file).
   - the module-level scratch `REAL(kind=dp) :: A(NREACT)` +
     `!$OMP THREADPRIVATE(A)` is dropped; each routine that uses `A` gets a
     routine-local declaration instead (a module-level `A` would race between
     GPU threads).
   - `USE gckpp_Global, only : DO_FUN` is dropped; the module instead declares
     `LOGICAL, PARAMETER :: DO_FUN(NVAR) = .TRUE.` so the compiler
     constant-folds the `IF (DO_FUN(i))` autoreduce guards.
2. `gckpp_Jacobian.F90`
   - `!$acc routine seq` on `Jac_SP`; `DO_JVS` becomes a local
     `LOGICAL, PARAMETER :: DO_JVS(LU_NONZERO) = .TRUE.`.
3. `gckpp_LinearAlgebra.F90`
   - `!$acc routine seq` on `KppDecomp` and `KppSolve`; `DO_SLV` becomes a
     module `LOGICAL, SAVE :: DO_SLV(NVAR+1) = .TRUE.` with
     `!$acc declare copyin(DO_SLV)` for device visibility.

Note: this mode constant-folds the autoreduce masks, i.e. it targets the
"AR off at runtime" configuration that the batched GPU solver uses. Runtime
autoreduce is incompatible with GPU mode by design (same semantics as the
patch script).

## What a real upstream PR to KPP would still need

- **Generality**: only the F90 backend is handled; C/F77/Matlab silently
  ignore the flag (should at least warn). `KppSolveTR`, `Fun_SPLITF`-style
  extras in other configurations, Hessian/Stoichiometry files are not
  annotated.
- **Interaction rules**: `#ACCDIRECTIVES on` + runtime autoreduce is
  semantically "masks always .TRUE."; a real PR should either error when the
  user requests runtime AR on GPU or emit device-updatable masks. Also
  untested with `#DECLARE VALUES` (symbolic sizes would need literals there).
- **The integrator itself**: this mode makes the *mechanism* files
  GPU-ready; the batched/offloaded integrator (`gckpp_BatchIntegrator.F90`)
  still lives outside KPP. Upstreaming would mean adding a batched
  rosenbrock driver under `int/` or documenting the external-driver contract.
- **Tests**: KPP has `ci-tests/`; the PR needs a small mechanism test that
  (a) diff-checks flag-off output byte-identity, (b) compiles the flag-on
  output with a device compiler in CI.
- **Docs**: `docs/source/using-kpp/04-input-for-kpp.rst` entry for the new
  command; CHANGELOG.
- **Review items**: the `KPP_ACC_ROUTINE` placeholder-in-sed mechanism in
  `IncludeCode` is pragmatic but fragile (line-anchored sed on included
  files); the `accRoutineSeqNext` one-shot global is not thread-safe (KPP is
  single-threaded, but reviewers may prefer an explicit argument);
  `Fun_SPLITF` is hand-printed `fprintf` code and was patched in kind.
